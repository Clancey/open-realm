# StarCraft II M3 Model Format

M3 is the binary 3D model format used by StarCraft II (and Heroes of the Storm). OpenWarcraft3 includes an M3 loader so that StarCraft II assets can be rendered alongside Warcraft III content.

## Overview

Unlike chunked MDX, an M3 file uses a versioned reference table. A field `Reference` is
`(nEntries, ref, flags)`: `ref` is an index into the header's `ReferenceEntry` table, **not a byte
offset**. The selected entry supplies the four-byte section ID, byte offset, element count, and
section version. Section bytes end at the next greater reference offset (or the reference table).
Four-byte IDs are compared in file byte order: semantic `MODL` is stored as `LDOM`, for example.

## File Header

```
DWORD  magic       // 'MD34' or '43DM' (little-endian)
DWORD  refOffset   // byte offset of the reference table
DWORD  refCount    // number of Reference entries
Reference modelRef // exactly one root record whose file-order section ID is LDOM
```

The file is divided into two regions:
1. **Data region** — packed binary data for all structs.
2. **Reference table** — `ReferenceEntry { id[4], offset, nEntries, version }[]`.

## Core Types

```c
typedef struct {
    DWORD  nEntries; // number of elements
    DWORD  ref;      // index into ReferenceEntry[]
    DWORD  flags;    // usually 0
} Reference;
```

The declaration is valid only when `Reference.nEntries == ReferenceEntry.nEntries`, the section ID
matches the field's schema, and the physical bytes contain the version-specific disk stride. Host
struct sizes are never disk strides: parsed structs contain pointers and renderer fields absent from
the file. Observed WoL strides include:

| Record | Versions and disk strides |
| --- | --- |
| Standard material | v15 268, v16 280, v17 340 |
| Layer | v22 356, v24 436, v25 468 |
| Region | v3 36, v4 40, v5 48 |
| Sequence | v0-v1 96, v2 92 |
| Timeline / validator / getter | 204 / 28 / 24 |
| Bone / division / batch | 160 / 48 / 14 |
| Animation FLAG / EVNT | FLAG v0 4; EVNT v0 100, v1 104, v2 108 |

Normal alignment padding may follow the last record, so validation requires enough bytes for the
declared records rather than exact section-length equality.

The animation record sizes and field introductions are cross-checked against the public
[SC2Mapster m3addon schema](https://github.com/SC2Mapster/m3addon/blob/master/structures.xml);
unknown versions remain rejected rather than being interpreted as a known layout.

Primitive aliases used throughout the format:

| Alias | C type |
|-------|--------|
| `m3Float32_t` | `float` |
| `m3Vector2_t` | `VECTOR2` |
| `m3Vector3_t` | `VECTOR3` |
| `m3Vector4_t` | `VECTOR4` |
| `m3Matrix4_t` | `MATRIX4` |
| `m3Pixel_t` | `COLOR32` |
| `m3Face_t` | `USHORT` |

## Animation References

Animated scalar and vector values are represented by `AnimRef` structs. Each `AnimRef` embeds the initial/null value directly and carries an animation ID referencing an animation sequence data block:

```c
typedef struct {
    USHORT interpolationType; // 0=constant, 1=linear, 2=hermite, 3=bezier
    USHORT animFlags;
    DWORD  animId;            // index into ANIM table, or 0xFFFFFFFF
    <type> initValue;
    <type> nullValue;
    DWORD  unknown;
} m3<Type>AnimRef_t;
```

Typed variants are declared for `Pixel`, `Uint16`, `Uint32`, `Float32`, `Vector2`, `Vector3`, and
`Vector4`. Runtime animation access uses `SC2_M3ReferenceCount()` and
`SC2_M3ReferenceElement()`: both revalidate declaration count, file-order section ID, element
stride, index multiplication, and physical byte bounds before copying one element. Raw reference
pointers must not be indexed by animation-authored counts.

## Geometry

The geometry section contains:

- **Vertices** — position, normal, tangent, UV coordinates, and up to 4 bone weights/indices per vertex.
- **Faces** — triangle index list (`m3Face_t` = `USHORT`).
- **Bone lookup table** — maps per-vertex bone indices to the skeleton's actual bone indices.

`games/starcraft-2/common/sc2_m3.c` owns byte parsing. The desktop renderer consumes that parsed
model and creates GPU resources separately. The authored vertex stream uses a 28-byte base, four
bytes per UV set, and four optional vertex-color bytes. Observed WoL declarations are:

| `vertexFlags` | UV sets | Disk stride |
| --- | ---: | ---: |
| `0x0180007d` | 1 | 32 (zero-geometry effect models in TRaynor01) |
| `0x0182007d` | 1 | 32 |
| `0x0186007d` | 2 | 36 |

The desktop upload currently retains UV0 only and converts the packed normal to floats:

```c
// Attributes consumed by renderer/shaders/m3.vert:
in vec3 i_position;
in vec4 i_color;
in vec2 i_texcoord;
in vec3 i_normal;
in vec4 i_skin1;        // bone indices (4 × uint8, packed in float4)
in vec4 i_boneWeight1;  // bone weights (4 × float)
```

The shared shader declares `mat4 uBones[128]`. Region-local `firstBoneLookupIndex` is required when
mapping authored per-vertex indices through the model bone lookup table.

## Materials

M3 materials reference textures through a `Reference` to an array of `m3Layer_t` structs. Each layer includes:

- a texture `Reference` (points to a `Reference` of path strings)
- an `AnimRef` for UV offset and scale animation
- flags controlling blending, UV wrapping, and normal-map usage

Desktop policy is not a format fact: it currently samples diffuse only, forces two-sided drawing,
and disables fog. Layer 2B1 preserves all standard-material/layer records and marks unverified
material flags, animated-layer evaluation, composite evaluation, and nonstandard material kinds
unsupported rather than copying those desktop choices.

## Bones and Animation

The skeleton is stored as an array of `m3Bone_t` structs, each containing:

- parent bone index
- initial transform (`m3Matrix4_t`)
- `AnimRef`s for translation, rotation, scale
- a bounding sphere used for culling

Animation sequences are stored as `m3Sequence_t` entries. Each sequence specifies:
- start and end frame numbers
- movement speed
- bounding sphere for the whole sequence
- a `Reference` to per-sequence data blocks (containing the actual keyframe arrays for every `AnimRef` in the model that changes in that sequence)

## Bounding Volumes

Every node and sequence carries a `BoundingSphere` struct:

```c
typedef struct {
    VECTOR3 min;
    VECTOR3 max;
    float   radius;
} BoundingSphere;
```

Collision shapes are defined separately as `BoundingShape` structs with a shape type (sphere / capsule / box), a reference bone, and a transform matrix.

## Versioning

M3 reference-table entries carry a section version. The reader uses a versioned macro
`M3_READ(buffer, var, version)` that reads baseline fields when `version == 0` and later fields only
when the section version exceeds the supplied threshold:

```c
#define M3_READ(BUFFER, VAR, VERSION) \
    if ((BUFFER)->ent.version > VERSION || VERSION == 0) \
        M3_Read(BUFFER, &VAR, sizeof(VAR));
```

This allows the same reader code to handle multiple revisions of the format. `VERSION=0` is a field
threshold, not a declaration that the section cannot itself be version zero. Retail `_GTS` v0 and
`_STS` v0 records still contain their baseline `Reference` fields and consume 24 and 28 bytes
respectively.
